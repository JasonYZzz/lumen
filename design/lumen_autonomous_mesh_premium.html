DESIGN PHILOSOPHY

让自治有边界，
让执行有证据。

01 / CONCURRENCY SAFETY

Lease + Fencing Token

同一 Run 只允许一个有效 Attempt。旧 Worker 失去租约后无法提交状态，防止脑裂和重复副作用。

02 / SIDE-EFFECT SAFETY

Idempotency + Outbox

使用稳定的业务意图键和数据库 Outbox。外部 Action 超时先查询，再判断是否需要再次调用。

03 / END-TO-END TRUST

Verify → Commit → Ledger

测试或业务系统确认通过后，提交工作流状态与可靠通知事件；投递失败独立重试并记录回执。

05 / POLICY & GUARDRAILS

Agent 做决定，Policy 授权行动

越是靠近生产数据、支付与部署，自治范围越窄。以下四级策略是建议的初始边界；具体金额、角色和环境阈值需要企业配置。

L0 / READ-ONLY

只读自动执行

查询 Issue、拉取日志、读取订单、检索关联对象；资源级鉴权和审计仍然强制执行。

L1 / SANDBOX

沙箱内自治

克隆临时仓库、生成补丁、运行单测 / Eval、创建草稿 PR；隔离工作区与生产 Secrets。

L2 / APPROVAL

需要审批放行

受保护分支合并、生产部署、敏感订单调整、库存预留等按租户策略进行门禁。

L3 / RESTRICTED

独立强授权

退款、扣款、改价、删除生产数据等禁止模型直接写入，交由专门业务授权通道。

Action Policy Playground

可交互的静态策略演示，不连接实际环境，也不会执行真实 Action。

POLICY DECISION / SIMULATION ONLY
ALLOW

只读操作通过基础策略门禁。实际运行仍须校验 tenant_id、actor_id 和目标对象 ACL。

MATCHED RULE · READ_ONLY_ACCESS
关键安全设计：代码执行沙箱禁止共享高权限 Shell / 生产 Secrets；业务写入必须经过独立的 Action Gateway，重新验证授权、对象版本、幂等键及审批摘要。模型输出永远不是授权令牌。
06 / ENGINEERING CONTRACTS

统一能力契约，隔离业务实现

TaskDefinition、ActionDefinition、ActionInvocation 和 EvidenceRecord 是扩展关键。业务方提交动作契约，而不是把生产 API 任意暴露给大模型。
