四条平台硬边界

设计约束

决策 ≠ 授权

Agent 只产生 Proposal；独立 Policy Engine 决定动作能否执行。

模型输出 ≠ 事实

校验只能基于真实 CI、日志、业务回执和可追溯证据。

会话 ≠ Task Run

Run 与 Attempt 跨进程持久化；对话日志不能替代工作流状态。

幂等 ≠ Exactly Once

外部副作用需要幂等键、结果确认和不确定状态对账。

    04 /

    任务执行状态机 · 失败恢复 · 一致性设计

    不能把“模型回答完成”视为“任务成功”。任务完成的判定应由独立的 Verifier 读取真实结果证据并触发状态提交。部署重启后基于持久化 Checkpoint 恢复逻辑任务，不假设原本的 DSH 子进程仍然存活。

    Durable Task State Machine · 核心正向路径
    CREATED→DEDUPED→CONTEXT_READY→PLANNED→POLICY_CHECK→EXECUTING→VERIFYING→COMMITTING→SUCCEEDED
    异常 / 人工控制分支
    WAITING_APPROVAL↔RESUMEDRETRY_SCHEDULED↔EXECUTINGNEEDS_RECONCILIATION→COMPLETED / FAILEDCOMPENSATING→COMPENSATED / MANUAL
    Checkpoint 持久化：workflow step + action state + source object version + model/prompt/tool/policy versions + artifact refs + approval token + fencing token。重试前先读取目标动作的提交状态并向外部系统查证，不能对未知结果盲重发。

    最重要的六项可靠性机制

    01 / Stable Task Identity

    task_key = tenant + source + event_id + action_type。同一事件去重，必要时基于目标对象版本建立新任务。

    02 / Lease + Fencing

    同一 Run 限定活动执行者；租约续期与 fencing token 阻止旧 Worker 回写，避免脑裂。

    03 / Checkpoint + Resume

    阶段结果、产物路径和审批输入持久化；恢复从最近已确认边界继续，而非重复外部副作用。

    04 / Transactional Outbox

    任务提交与待投递事件写入同一 DB 事务；投递器持续投递并由下游幂等去重。

    05 / Reconcile Unknown

    写请求超时必须转 NEEDS_RECONCILIATION，使用业务请求 ID 回查；不把 timeout 自动判定失败。

    06 / Saga & Compensation

    库存预占、配送创建等跨服务操作采用明确补偿或人工修正路径；补偿也需要幂等与审计。

    执行边界与恢复条件

    步骤成功提交条件失败 / 不确定时处理恢复原则
    读取来源来源可读且获取了可验证的增量游标标注 source unavailable，不移动对应 Bookmark重试该来源、其他来源可以部分完成
    Agent 规划计划结构化且策略、工具、版本快照完整解析失败仅重试规划；超过预算转人工重启 DSH 可从持久化 Plan 继续
    外部 Action领域 API 返回成功 + 操作回执可回查超时 → Unknown，不能立即重发扣款/退款幂等键查询已处理结果，再决策是否重试
    Verification真实测试/业务状态达到预期，证据已保存失败回滚/修复/审批；不伪造 pass只重跑可安全重复的验证节点
    通知和结算目标系统回执确认，台账与游标同批次提交投递不确定留未提交状态并回查按 Ledger / Outbox / receipt 判重
    05 /

    Policy Engine：按风险级别控制自治边界

    风险由动作类型、对象环境、影响范围、敏感度、金额、可逆性、租户策略共同决定。以下策略矩阵是建议初始配置，不代表已经验证过的生产阈值。

    LEVEL 0Read-only

    允许自动执行

    查 Issue、拉取日志、查询订单、生成诊断报告。只读凭据与数据最小化。

    LEVEL 1Sandbox

    隔离自治执行

    创建临时分支、生成 Patch、运行 CI、回归测试、创建草稿 PR。

    LEVEL 2Approval

    人工或规则放行

    合并受保护分支、生产部署、库存预留、政策内重要订单变更。

    LEVEL 3Restricted

    默认阻断直写

    退款、扣款、资金划拨、删除生产数据、改价等敏感操作，需专门授权通道。

    交互式策略判定示例

    仅演示规则 · 不调用真实系统
    ALLOW · 只读操作

    符合最小权限原则。生产环境读取敏感数据仍须校验租户、资源级权限与审计。

    策略决策输入还应包含 tenant_id、actor_id、object_id、object_version、preconditions、amount、policy_version、run_id、action_hash。真正执行时必须在提交边界重新授权。

    Agent 工作区与真实生产系统必须硬隔离

    Code Execution Sandbox

    在受限容器/临时工作区中运行不可信测试代码：非特权用户、只读基础镜像、CPU/内存/时长限制、网络出口白名单、短期凭据、敏感路径隔离。来自外部 PR 的代码不得获得生产密钥。

    禁止共享宿主机高权限 Shell

    Business Action Gateway

    Agent 不直接连接生产数据库和支付 API；所有写入经类型化 Action、双重鉴权、目标版本 CAS、幂等键、审批凭证核验，并记录外部系统回执。

    授权与业务回执双校验

    建议的数据表 / 资源

    资源关键字段设计要点
    task_definitionstype, trigger, policy, workflow_version, timeout任务模板版本不可变；Run 绑定特定定义快照
    task_runs / attemptsrun_id, state, lease_owner, fencing_token, checkpoint_refCAS 更新、重启恢复、重试次数及预算
    ontology_objects / linkstype, id, props, source_version, synced_at, tenant语义投影，回源时使用版本校验与 freshness 限制
    action_invocationsaction_id, idempotency_key, expected_version, receipt, status外部动作账本，UNKNOWN 必须对账后再执行
    approvalsaction_hash, approver, scope, expires_at, consumed_at授权绑定目标动作、数量/金额/状态与有效期
    source_bookmarks / ledgersource, cursor, seen_id, result, committed_at增量消费，避免漏读与重复外部影响
    outbox_events / evidenceevent_id, delivery_state, artifact_uri, trace_id可靠投递及审计证据的存储索引

    建议的 API 边界

    POST /v1/tasks创建业务任务；返回 task_id、dedupe_key 和租户作用域。
    GET /v1/tasks/{id}查询 Run / Attempt、阶段、证据与阻断原因。
    POST /v1/tasks/{id}/approve绑定 action_hash 的签名审批，过期或版本不符拒绝。
    POST /v1/tasks/{id}/resume人工继续；生成新的 Attempt 和 fencing token。
    POST /v1/tasks/{id}/cancel取消后续动作；已提交外部副作用走补偿/人工修复。
    GET /v1/tasks/{id}/eventsSSE 流展示决策、工具、测试、审批、状态变化。
    建议同时版本化 Ontology Schema / Action Schema / Policy / Workflow / Prompt / Model / Tool Bundle / Eval Dataset。恢复一个旧 Run 时，必须确认其绑定资源仍兼容，避免“旧状态 + 新语义”导致错误执行。
    07 /

    推荐技术栈与集群部署方案

    考虑现有 Java + Python + DSH 工具链，建议在外围用 Java/Spring Boot 管理稳定业务 API 和工作流，用 Python DSH Worker 执行 Agent 推理和局部工具链。持续任务的恢复由外层持久化执行系统负责。

    架构能力推荐选型理由 / 备选
    统一 API / ConsoleSpring Boot / FastAPI + SSEJava 负责企业业务服务；FastAPI 适合 Agent Adapter；对外统一 OAuth2/OIDC 和 RBAC。
    Durable OrchestratorTemporal（中长期）长流程、定时、重试、Saga、人工审批；MVP 可 Postgres + Job Queue，但需要自行补齐恢复语义。
    Agent RunnerDSH Python SDK + 独立 Worker每个 Attempt 显式指定 dsh_home、workspace、profile；子进程与调度器隔离。
    Ontology / QueryPostgreSQL JSONB + 关系表起步先定义 Object / Link / Action Schema；多跳复杂或强图查询再扩展 Neo4j（可选）。
    领域工具与动作Typed Adapter + MCP / HTTP / SDKGitHub、Issue、CI、OMS、WMS、Payment SDK 均经过 Action Gateway，不直接让 LLM 自由写入。
    代码验证 / Agent Evalpytest / JUnit / Playwright / CI + 自研 Eval Gate判定规则优先基于确定性断言；LLM Judge 只能作为一类有版本和可信度的证据。
    状态 / 索引 / 产物PostgreSQL + Milvus + OSS业务运行状态入 PG，文本上下文入 Milvus，日志附件、测试报告、diff 放 OSS。
    可观测OpenTelemetry + Tempo / Loki / Grafana统一 trace_id / task_id / run_id / attempt_id / action_id，实现单任务全链路审计。
    Sandbox隔离容器执行池 + 最小权限运行不可信代码应采用进程和文件系统边界、资源配额、网络隔离及短凭证。

    推荐物理部署拓扑

    Web / UI / CI / Event→API Gateway (N replicas)→Temporal Server / Queue→Workflow Workers (N)→DSH Task Workers→Sandbox / Typed Action API

    Control Nodes

    无状态 API；Workflow 持久化；审批与策略中心；任务元数据和 Outbox。

    Agent Worker Pool

    一个执行租约对应可终止的 DSH 进程 / 隔离 workspace；进程消失不代表 Run 消失。

    Domain & Evidence Plane

    CI、Git、OMS、WMS、数据库、对象存储、Tracing；外部写必须幂等回查。

    恢复路径：Worker 丢失 → Lease 超时 / Workflow 重派 → 新 Attempt 获得 fencing token → 加载持久化 Task、Plan、Action Ledger 与证据 → 对未确认 Action 执行回查 → 重建 DSH 工作区 → 从安全边界继续。无需强制把用户绑定到某台旧 Worker。

    落地建设优先级与验收标准

    不建议第一阶段就做“万能多 Agent 平台”。先在低风险的代码修复与自动测评上验证系统可靠性，再建立跨领域 Ontology Action 标准，最后引入交易型业务。

    PHASE 01任务控制

    阶段 A · 自动 Bug 修复（首个 POC）

    选一个 Git 仓库与 CI，构建 Issue/Webhook → 日志与代码检索 → 可重现失败 → Patch → Unit/Integration Tests → 草稿 PR → 人工审批。首先禁止自动合并、自动生产发布，形成证据完整、可追踪的闭环。

    阶段 B · 自动化测评平台

    把测试用例与 Agent Eval 统一成可版本化的 Eval Suite：确定性指标（构建、测试、覆盖率、SAST）、模型指标（正确性、引用证据、越权率、业务规则遵循）与人工复核分开存储，建立失败回流与基线对比。

    阶段 C · Ontology Action 与订单试点

    优先只读订单查询、异常归类、待处理建议；经过对账验证后尝试白名单、额度受限、可逆的库存预留等动作。退款、支付、资金相关行为保持独立强授权并优先人工处理。

    建议观察的关键指标（定义与目标需在试点校准）

    指标计算口径用来发现什么
    Verified Completion Rate真实核验通过的任务数 / 有效任务数避免把 Agent 自称“已完成”当成功
    Auto-Fix Acceptance Rate被人工接受的自动修复 PR / 自动生成的可审 PR修复建议有多少可用
    Regression Escape Rate放行后在观察期内出现回归的变更 / 放行变更测试门禁是否足够
    Unsafe Action Rate越权执行成功事件数 / 全部高风险动作请求数安全边界是否真正有效（目标应为 0）
    Recovery Success Rate恢复后完成或进入明确人工终态的中断任务 / 可恢复任务部署重启与异常恢复的稳定性
    Duplicate Side-Effect Rate重复创建有害业务副作用的 Action / 实际 Action 执行数幂等、Outbox 与对账是否有效
    Cost per Verified Task模型 + 工具 + Sandbox + CI 成本 / 真实完成任务避免只优化 token，而忽视验证总成本
    建议的第一条产品能力：“自动修复 GitHub Issue 并完成 CI 验证，生成待审批 PR”。这个场景最容易严格判断成功与失败，能验证平台 80% 的通用机制：触发、Ontology 实体解析、规划、执行、验证、审批、记录与重启恢复。这里的 80% 是设计上的定性估计，不是实测数据。
