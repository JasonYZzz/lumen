# Lumen Web / TUI 交互研究与升级记录

日期：2026-09-03。性质：源码审计、产品参考研究与本次实现快照；不是新的 Runtime 规范。

## 1. 结论

Lumen 原有能力已经覆盖对话、模型、审批、计划、工具、工作对象、子 Agent、历史与实时语音。
主要问题在于这些能力的**呈现层级与操作路径**：部分命令先输出文本再要求用户重新输入；
计划把大量步骤说明直接铺在正文中；处理过程、中间回答与最终交付争夺阅读空间；
输入区同时暴露过多设置，却没有一个适合鼠标操作的统一动作入口。

本次把 Web 的日常路径收敛为：**读回答 → 在同一输入框继续 → 按需打开动作或详情 → 回到原草稿**。
视觉以用户提供的 ChatGPT 最新页面为直接参照：窄阅读列、低对比背景、紧凑圆角输入框、等宽动作菜单、
图标与自然语言动作名称、弱化说明、二级选择、正文与辅助内容分层。
TUI 保持终端的键盘效率，将同一行为翻译成选择器、快捷键、折叠计划与现有审批提示。

计划需要额外保留 Lumen 的领域语义：计划内容、步骤进度、方案确认、工具审批、Run 终态是不同概念。
所有 UI 都只投影已有状态，不能因为“6/6”就声称获得执行授权或完成整个任务。

## 3. 现状根因：相同能力被不同入口表达成了不同交互

### 3.1 模型切换

原 TUI 的 `/model` 主要列出模型，用户需要读名称再输入命令；原 Web 能点选，但选项的重复说明占用空间，
slash 补全与直接选择也不够一致。输入“模型”时，用户的目标通常是做选择，而不是获得一段帮助文本。

升级后的行为：

1. Web 点击当前模型、快捷菜单的“模型”或执行 `/model`，打开同一可搜索选择器。
2. TUI `/model` 或 `Alt+P` 打开模型选择器，方向键与 `Enter` 确认，`Esc` 返回草稿。
3. `/model <configured-name>` 继续支持精确切换，已有脚本习惯不失效。
4. 选项来自真实模型注册表；当前值打勾；没有匹配项有明确反馈。
5. 切换经过已有 Host Interface；运行中拒绝变更。Web 展示处理中与失败状态，成功后刷新真实当前值。
6. 不把模型列表第一项冒充当前模型，不用模型名猜测图片能力、effort 档位或价格。

Web 当前模型选择是工作区运行配置，对下一轮生效，不能包装成每条历史消息独立换模型。

### 3.2 slash 菜单与直接操作

ChatGPT 截图的关键是“可读的动作列表”：使用动作名称吸引视线，说明紧随其后，进入更多选择时才出现箭头。
Lumen 原菜单把 monospace 命令放在最显眼位置，适合熟练用户，却增加了第一次使用的认知成本。

本次实现：

- Web 菜单改为输入框等宽、单列、44px 行高、语义图标、自然语言动作名称和弱化说明。
- `+` 打开图片、模型、计划、审批、复制、创建任务、分支、工具与技能的常用操作；不用清空草稿输入 `/`。
- `/` 保留完整命令发现；按命令名、中文说明和关键词过滤。模型与审批参数不再占满初始菜单。
- `/model alpha` 过滤时精确名称优先于 `alpha-pro`，避免接受补全时选错模型。
- Web `Enter` 执行完整命令，参数未填完时先补全；`Tab` 只补全；中文输入法确认候选不发送消息。
- TUI 只对整段输入的 `/model`、`/mode`、`/tasks` 在首次 `Enter` 时直接打开，保留其他已有补全语义。
- 不支持图片的模型仍可使用快捷菜单；只有图片入口禁用，且说明原因。

这不是另建一套命令执行器。菜单只给出已有命令或本地上传动作，模型与审批仍使用原有应用层契约。

### 3.3 工作方式与审批

“先规划”回答的是先研究方案还是开始执行；“每次确认 / 自动接受修改 / 自动执行”回答的是工具如何审批。
二者混在一个选择器里会让用户误以为批准计划等于放开全部工具权限。

Web 在输入框旁分别显示工作方式与审批模式。审批选择器独立修改审批策略；兼容 `/mode` 的组合语义仍保留：
`/mode plan` 进入 Plan，`/mode manual` / `accept_edits` 回到 Default 并设置相应审批。
TUI 的模式选择器和 `Shift+Tab` 沿用已存在的模式循环和安全行为，没有为了对齐竞品而偷偷改变授权范围。

## 4. 计划面板：本次最重要的结构升级

原 Web 计划采用多列步骤和常驻长说明。一个步骤带大量 evidence、note 或实施细节时，
用户难以快速回答三个问题：“现在到哪一步？哪里卡住？我是否需要确认？”
横向排列也破坏了有先后关系的任务阅读顺序。

### 三层阅读结构

| 层级 | 默认显示 | 何时展开 | 设计依据 |
|---|---|---|---|
| 对话中的计划摘要 | 生命周期标签、当前/受阻步骤、完成数量 | 点击摘要 | 快速定位进度，不打断正文阅读 |
| 最新计划侧栏 | 目标、版本、进度、单列有序步骤、每步状态 | 右上角“计划”或 `/tasks` | 把持续更新的工作状态放到独立详情区域 |
| 单步详情 | 默认折叠 note、依赖与验收条件 | 点击“查看说明” | 长解释只在需要核查时出现 |

右侧面板在窄屏占满宽度；正文和详情分别滚动。关闭按钮、`Esc`、点击遮罩均可关闭，
关闭后恢复到触发控件。步骤状态同时使用图形与文字，避免仅靠颜色区分。
停止运行后不会保留旋转图标制造仍在执行的错觉。

### 进度显示规则

| 状态 | 表达 | 是否计入完成 |
|---|---|---|
| pending | 待开始、空心标记 | 否 |
| in_progress | 进行中；仅真实运行时使用动效 | 否 |
| completed | 已完成、勾选标记 | 是 |
| blocked | 受阻、警示标记，优先进入摘要 | 否 |
| skipped | 已跳过、减号标记，另列数量 | 否 |

空计划不会显示成功。全部步骤结束但含跳过时显示“步骤已结束”，不把跳过归为完成。
`review_pending`、`rejected`、`cancelled`、`blocked` 等 lifecycle 的语义不能被步骤计数覆盖。

### 方案确认

确认区移到输入框附近，显示“方案已就绪，等你确认”、当前版本和执行时的审批策略。
用户可以查看完整计划，展开调整意见，或确认开始执行。提交过程中禁用重复操作；
使用已有带 revision 的 review Interface，保留版本冲突和后端权限检查。

TUI 对应为可聚焦计划、`Enter` / `Space` 折叠、`E` 展开说明，`Alt+T` 或 `/tasks` 快速定位。
原实现没有完整处理 skipped 的图标分支，本次补齐，同时对标题和说明按字面呈现，避免 Rich markup 改变内容含义。

## 5. 回答、过程、代码、历史与响应式

| 区域 | 本次升级 | 保留的语义 |
|---|---|---|
| 正文 | 800px 阅读列，15px 基础正文，移除助手正文额外缩进 | Markdown、安全文本渲染和已有引用 |
| 输入区 | 紧凑圆角输入框，左侧 `+`，右侧发送/停止/已有语音入口，设置在近旁 | 多行、输入法、光标高亮、文件提及、图片能力检查 |
| 处理过程 | 默认折叠；当前待审批仍自动展开 | 工具失败与历史完整可查 |
| 中间说明 | 同一轮工具调用前的助手说明归入处理过程 | 只生成 UI 投影，不改写 journal 或原始消息对象 |
| 代码 | 语言栏和独立复制按钮，成功/失败反馈 | 不执行代码，不启用不可信 HTML |
| 表格 | 独立可聚焦横向滚动区域 | 不撑开整页或截断列 |
| 历史 | 标题搜索、空结果提示、桌面侧栏收起 | 原有重命名、归档、恢复、删除、所有权与活动任务限制 |
| 移动端 | 390px / 320px 检查；面板全宽、正文减少边距；离屏侧栏不可聚焦 | 同一真实数据与 API，不另造移动端状态 |
| 排队输入 | 修复 `/dequeue` 撤回后又清空恢复文本的问题 | 既有 steer / follow_up 队列 |

对已完成且有后续最终回答的中间文本进行归类，保留没有工具穿插的连续回答。
这种视觉分层比复制每一条事件卡片更有价值：用户先得到答案，需要证据时再打开过程。

## 7. 实现与权威分工

| Module / Interface | 职责 |
|---|---|
| `WorkspaceHost` | 模型、Session、运行互斥、审批与命令的既有权威；本次不新增运行时权威 |
| `choice_picker.py` | TUI 模型与模式共用选择 Implementation，返回被选值 |
| `ChoiceMenu` | Web 可搜索选择、焦点恢复、异步反馈与错误呈现 |
| `Composer` / slash registry | 输入、补全、可见动作和键盘语义；选择后调用已有命令 |
| `plan-presentation.ts` | PlanState 的只读派生展示；不持久化、不授权、不推进 Run |
| `PlanPanel` / `PlanDrawer` | 摘要、单列步骤、详情与弹层生命周期 |
| `turn-activity.ts` | 将已有 timeline 分为正文与过程；不产生新 Session 事实 |
| `CopyButton` / Markdown rendering | 统一回复与代码复制反馈、安全 Markdown 和宽表格 |

删除与替换的证据：

- 原 `lumen-app.tsx` 内部 PlanPanel / step icon 已由抽出的同一 PlanState 展示完全替代，生产调用统一指向新实现；不保留两套状态映射。
- TUI 裸 `/model`、`/mode` 的静态列表输出分支被真实选择器替代。对应旧测试改为公开输入路径与选择结果测试。
- 原 Web 重复剪贴板处理由同时服务回复和代码的 CopyButton 替代；新 Module 吸收反馈、失败和计时清理，具有两个真实调用方。
- 移除只服务旧计划两列/直接子节点排列的 CSS 规则，其目标 DOM 已被替代。

保留：显式模型参数、模式兼容命令、Host busy 检查、auto 的已有确认路径、Plan revision 检查、
Session journal、SSE 恢复、工具审批、Sandbox、Agent 生命周期、附件校验、历史分支与归档保护。
未改动 Runtime 调度、模型 Provider、Session schema、OpenAPI schema、Work Product mutation 协议。
当前工作区已有大量其他未提交架构修改，本次未重置或覆盖它们。

本次实际结果：Web 56 项通过；Python 交互及快照相关测试 169 项通过（含 56 个通过的视觉快照）；
Host / Web API 31 项通过；Ruff、Pyright、TypeScript、Next production build、命令契约和架构 Atlas 检查全部通过。
已通过生产静态页面复验，并恢复浏览器默认尺寸、清空合成验证草稿。
截图与键盘检查不足以证明全面无障碍合规；
尚未做真实屏幕阅读器、多浏览器、慢网全矩阵和可用性访谈，也没有声称这些结果已通过。

完整产品对齐仍有需要独立产品契约的差距，不能用装饰性按钮冒充实现：

| 能力 | 当前事实 | 合理的后续实现约束 |
|---|---|---|
| 推理强度 / 自动模型路由 | Lumen 未给 Web 暴露统一、按模型验证的完整能力契约 | 先由 Provider / Host 提供可选值、默认值与作用范围，再添加选择器；不硬编码竞品的“极高”等档位 |
| Artifact 编辑和版本对比 | 已有工作对象与验证契约；本次只升级计划详情 | 编辑入口必须穿过 TaskWorkspace mutation / verify Interface，不能直接写文件绕过验证 |
| 任意文档上传 | Web 现有上传入口针对图片，文件通过工作区 mention 提供 | 新增文档 ingest、大小限制、存储引用与解析契约后再开放，避免标签声称支持而实际上丢失内容 |
| 分享 / 发布 | 未新增外部分享路径 | 先设计可分享范围、脱敏与权限，不直接复制竞品分享按钮 |
| Web 主题 | 本次使用当前浅色体系；TUI 保留双主题 | 若新增 Web 深色模式，需要完整令牌、图表/代码/弹层对比度验证，不用颜色反转凑合 |
| 专家审计面板 | 原 Runtime / transcript 入口保留，仍有工程性术语 | 后续按真实高频任务减少术语；不能删除恢复、失败处置与 Agent 导入入口 |

本次完成的是现有 Web / TUI 能力的交互与视觉升级，以及针对完整产品面的研究和差距说明。
“贴近最新产品体验”的验收标准是操作可发现、当前状态可信、下一步清楚、草稿不丢、详情可追踪，
这些标准由真实行为验证，而不是仅靠复制颜色和圆角。
