主流 Agent 的外部 Agent 接入方案设计
Pi Agent · DeepSeek Harness · Codex · Claude Code

本报告拆解四套主流 Agent 运行时"如何把外部 Agent 接进来、如何把自己接出去"的工程设计。 两个重点对象： Pi Agent（极简内核 + 原语而非功能）与 DeepSeek Harness（ctx.subagents 能力缝、 静态能力协商、生命周期与权限边界），并在第 4 章做正面对撞分析。

一页结论（TL;DR）

  1. "外部 Agent 接入"其实有四种不同语义，混谈是绝大多数讨论失焦的根因：接外部工具（MCP）、接外部Agent（委派 / subagent provider）、被外部接入（自身作为 server / SDK）、接外部宿主（IDE / ACP）。四家各自站在不同层，不能简单比"谁更强"。
  2. 接入位置决定一切。Pi 把外部 Agent 伪装成一个"模型"（provider 层），最轻最巧；DSH 把它做成一等的能力缝（subagent 层），最重最完备；Codex 走双向 MCP（既是 client 又是 server）；Claude Code 走 SDK + hooks + subagents，把自己变成可编程组件。
  3. Pi 的洞察是"原语而非功能"。六个刻意不内建的能力（MCP / 子代理 / 权限弹窗 / Plan mode / 内置 Todo / 后台 bash）全部给出替代路径。其中最值得拿走的一条原则是：被拿掉的多半是"把状态藏在工具内部"的功能——状态应该落在你看得见、能版控、换工具也还在的文件里。这不只是省 token，而是决定出事时你能不能自己查。
  4. Pi 对外接与对内接用了两套机制。对外：provider bridge 把外部 Agent 注册成一个 provider（伪装成模型）；对内：委派不进内核，由第三方包 pi-subagents 用 Extension 实现，公开接口刻意只有「一个工具 + 一个命令」。Pi 把"要不要有子代理"重新定义成可安装、可替换、可自己写的问题。
  5. 最值得借鉴的接入契约是 DSH 的 ctx.subagents。它不是"能不能调 Claude Code"这种功能点，而是一套可复用的委派契约：命名注册表 + 静态能力描述符 + fail loud 的能力协商 + 显式的上下文继承语义 + 一次性/可继续双生命周期 + 分级停止阶梯。
  6. 两条被验证过的"反直觉"设计：① 依赖策略——DSH 不查 PATH、provider 自带依赖（版本确定性 > 顺从用户环境），Pi 则用精确 pin + min-release-age=2 + shrinkwrap 把供应链风险压到可审计白名单；② 权限策略——DSH 认证原生透传、只覆盖一个旋钮（permissionMode），且高风险 provider 默认 disabled: true 且不进 shipped bundle；Pi 则明确承认 packages 以完整系统权限运行、没有沙箱。两种回答都指向同一句话：能力越开放，默认值越不能友好。
  7. Pi 与 DSH 的本质差异是"继续运行的权力放在哪里"：Pi 把它集中在当前循环 + 三个宿主回调（steering / follow-up / shouldStopAfterTurn）；DSH 把它分散给模型 finish、工具结果、inbox、生命周期 hook、外围持久状态机并用只追加日志协调。复杂度没有消失，只是落在不同层。（详见第 4 章）
  8. 一个真实的缺口案例：AgentRQ 插件暴露出 DSH 不透传 MCP server 的 Instructions，导致模型"有工具但没有契约"，只能由插件自己在 system-prompt 里补。这提醒我们：能力接入 ≠ 契约接入，软约束的传递路径必须被显式设计。
  9. 对本项目（dongbi-agent-harness / AgentLoop v2）的适用性：DSH 的 subagent seam 是当前公开材料中最接近"生产级外部 Agent 接入规范"的样本；Pi 的会话树、状态外置、供应链清单与双层循环三个回调则是成本最低、最容易先落地的借鉴对象。建议按"注册表 → 能力协商 → 生命周期/取消 → 权限与默认开关"四步走（见第 7 章）。

0研究范围与方法

本报告回答一个问题：当一个 Agent 运行时需要"接入另一个 Agent"时，工程上应该怎么设计？ 这里的"接入"包括两个方向——往外接（把外部 Agent 当作我的子能力）和往外被接（让我自己能被别的系统当子能力用）。

选取四个样本的理由：

Pi Agent 重点对象

极简内核（4 个工具、约 300 词 system prompt、一棵会话树），主张 Primitives, Not Features。 对外用 provider bridge 把外部 Agent 接成"模型"，对内把委派做成可选第三方包。是"最少代码表达最多设计判断"的样本。

DeepSeek Harness 重点对象

MIT 开源、Node.js、开发者预览。以 Cordis"一切皆插件"为底座，把外部 Agent 做成一等 能力缝（capability seam）。当前公开材料中最系统的委派权限设计。

OpenAI Codex 协议双向

唯一同时提供成熟 MCP client + 官方 MCP server 模式的产品。codex mcp-server 暴露 codex / codex-reply 两个工具，用 threadId 跨进程续会话。

Claude Code 可编程组件

Agent SDK（Python/TS）把整个 Harness 变成可嵌入库：query() + hooks + subagents + MCP + Skills，并原生支持 ACP，是"被接入"最成熟的样本。

方法说明与证据边界 研究方法为公开资料桌面研究：官方文档与 npm/GitHub 包说明、第三方技术长文与源码结构分析、社区插件 README。 未能运行代码验证：DSH 仍处 Developer Preview（dsh-v0.1.1-rc.1 / 0.1.0-rc.x），官方明确警告会有破坏性变更；Pi 迭代同样快（pi-subagents 数周内从 0.28 走到 0.67）。 部分细节（如子代理 provider 的确切调用签名）在公开材料中未固定，报告中已逐处标注不确定性。所有来源 URL 与访问日期见附录。

1坐标系：先把"接入"这个词拆开

讨论"Pi / DSH / Codex / Claude 的接入方案"时，最常见的错误是把四种完全不同的东西放进同一张表比较。 先把语义分层，后面的对比才有意义。

四个关键判断

  • Pi 站在 L0/L1 之间，但两个方向都占。对外，它不接"外部 Agent"，它接"外部 Agent 的模型"——把外部 CLI 用 registerProvider 注册成 provider，让外部 Agent 在 Pi 里表现为一个可选模型。这是抽象层级上最取巧的一招：拿到了外部 Agent 的能力，却不用实现委派协议。对内，它把"委派"整体让给第三方 Extension 包（pi-subagents），内核不表态。而在 L3，它的 RPC / SDK 两个入口又使它自己成为最容易被别人接入的一方。Pi 的策略是：在每一层都只提供最小可用接口，把选择权交出去。
  • DSH 站在 L2，而且是唯一把 L2 做成"可替换能力缝"的。它的 ctx.subagents 与 ctx.llm、ctx.tools、ctx.sandbox 是同一级别的服务。"把任务交给 Claude Code"和"换一个沙箱后端"在架构上是同一件事。
  • Codex 的特殊性在于"双向"。它既是 L1 的消费者（MCP client），又是 L2 的提供者（codex mcp-server）。它是被 DSH 当作 subagent-codex 接入的对象——因为它提供了稳定的 app-server 协议。
  • Claude Code 的重心在"被接入"。Agent SDK 让任何系统都能把它 query() 起来；ACP 支持让它能塞进任何编辑器。它的接入方案本质是"把自己做成标准零件"，而不是"去接别人"。

2协议底座：MCP / ACP / A2A 的分工

四家的接入设计都建立在这三个协议之上。它们不是竞争关系，而是纵向互补的三层——这一点在 2026 年已被广泛接受， 但工程落地时仍经常被混用。

2.1 ACP v2 的一个信号：能力在"重新分层"

ACP v2（2026-07-20 发布为 draft，artifact schema-v2.0.0-alpha.3）做了一件很值得琢磨的事： 彻底移除了 client 侧的 filesystem 与 terminal 表面——clientCapabilities.fs、clientCapabilities.terminal、 fs/read_text_file、fs/write_text_file 以及全部 5 个 terminal/* 方法都被删除。 官方给出的理由是：采用率低，且 Agent 更倾向于使用自己的沙箱；如果 client 仍想提供这些能力，应该改为向 Agent 暴露一个 MCP server。

这个决定背后的判断是："Agent 该在谁的沙箱里跑"这个问题的答案变了。v1 假设宿主提供执行环境，v2 假设 Agent 自带执行环境。 这正是 Pi 那套桥接扩展（auto-allow 宿主 fs/terminal）会面临的边界问题，也是 DSH 选择"自带依赖、原生认证、只覆盖 permissionMode"的同源逻辑。

3四家方案逐一拆解

本章逐一拆解四家在"接入"这件事上的具体设计。其中 3.1 Pi Agent 与 3.2 DeepSeek Harness 是本报告的两个重点对象—— 它们恰好代表了两个极端：前者用最少的内核表达最多的设计判断，后者用最完备的契约把"接外部 Agent"变成可替换的一等能力。 两者的正面对撞放在第 4 章。

3.1Pi Agent：极简内核 + "原语而非功能" 重点

Pi（@earendil-works/pi-coding-agent，MIT）是四个样本中唯一的减法派。 GitHub 95.9k stars / 11.9k forks（2026-08-23 数据），但它的官方介绍读起来像一份"功能缺失清单"： 没有 MCP、没有子智能体、没有 Plan Mode、没有内置 Todo、没有权限弹窗、没有后台 bash。

它的设计主张一句话就能说完：Primitives, Not Features（提供原语，而非功能）—— "与其内建所有功能然后让你关掉不要的，不如给你原语自己组"。 内核只有三块：四个工具（read / write / edit / bash）、一条循环、一棵会话树； system prompt 控制在约 300 词（对比商业 Agent 动辄数千词、数十个预置工具）。

为什么"极短 system prompt"是一个工程决策，而不是审美 它同时买到三件事：① prompt cache 命中率最高；② 每轮 token 消耗最低； ③ 省下的上下文预算留给真正的 context engineering——决定什么进 context window、怎么管理它。 Pi 为此提供的抓手是：AGENTS.md（启动时从 ~/.pi/agent/、父目录、当前目录加载）、 SYSTEM.md（按项目替换或追加默认 system prompt）、自动压缩、可扩展的 compaction 实现、按需加载的 Skills。 Pi 的第一个可迁移结论是：把"固定占位"压到最小，把"可管理"放到最大。

3.1.1　设计主张：六项"刻意不做"与官方给出的替代路径

Pi 把"不做什么"列得比"做什么"更清楚，每一项都附上替代方案。这张表本身就是它的设计宣言：

刻意不内建官方理由替代路径
MCP工具描述会长久占用上下文，而多数任务用不到把工具写成带 README 的 CLI（走 Skills 让模型读 README 后用 bash 调用）；或装 pi-mcp-adapter
子代理编排方式在不同团队差异极大，不该由工具强绑一种用 tmux 开多个 pi instance；或装 pi-subagents；或自己写 extension
权限弹窗不假设你要哪一种安全模型放进容器隔离；或写一个符合自己环境的确认流程 extension
Plan mode不强迫所有人采用同一套规划仪式把计划写成 plan.md；或用 prompt template / extension
内置 Todo状态放在对话里容易让模型混淆用 TODO.md——跨 session 依然还在
后台 bash后台任务不易观察用 tmux：看得见，也能直接介入
这张表里藏着最值得从 Pi 拿走的一条原则 被拿掉的功能有一个共同特征：它们都是"把状态藏在工具内部"的功能—— plan mode 的状态、todo 的状态、子代理的内部脉络，全都在工具里。 Pi 的主张是：状态应该落在你看得见、能版控、换工具也还在的文件里。 这不只是省 token，而是决定了出事时你能不能自己查。

把它与 Everything Claude Code（214k stars，打包数百个现成命令与 agent）对照最清楚： Pi 从空开始让你填，ECC 从满开始让你删——对同一个问题的两种相反回答，没有绝对优劣，但选错会很难受。

一个容易忽略的信任边界设计 项目级资源（AGENTS.md 等）在非交互模式（-p、--mode json、--mode rpc）下默认被忽略—— 不弹提示、直接不用，需要时用 --approve 单次放行；交互模式下用 /trust 手动记录决定。 这是"无人值守默认保守"的一个干净实现：自动化场景不继承仓库里可能被投毒的指令文件。

3.1.3　会话是一棵树，不是一条聊天记录

  • 存储形式：会话自动保存到 ~/.pi/agent/sessions/，按工作目录分组；每个会话是一个 JSONL 文件，每条记录带 id 与 parentId，因此天然构成分支树——所有分支在同一个文件里，不需要多个文件。
  • 导航：/tree 跳转到任意历史节点并从那里继续（当前位置是 active leaf）；/fork 从历史用户消息开出一个新会话文件；/clone 把当前活跃分支复制成新会话。
  • 分支摘要：当 /tree 从一个分支切到另一个分支时，Pi 可以把被放弃的分支总结后附加到新位置，从而保留重要上下文而不重放整条分支。可选：不总结 / 用默认提示总结 / 用自定义关注点总结。
  • 其他能力：/compact [prompt] 压缩、/export 导出 HTML、/share 上传为私有 GitHub gist 并生成可渲染的分享链接；过滤模式 default / no-tools / user-only / labeled-only / all，Shift+L 给条目打书签。
  • 会话文件里装什么：消息条目、模型变更、思考等级变更、标签、压缩记录、分支摘要，以及扩展写入的条目。
Pi 最值得带走的一句设计判断："历史不是负担，而是可以重新进入的工作树。" 对 Coding 尤其自然——一次尝试失败，不必抹掉全部历史，回到分岔点保留旧路径、再试另一种实现。 它更像一种面向 Agent 会话的轻量版本控制，而不是只能不断向下滚动的聊天窗口。

3.1.4　扩展体系：五级杠杆，以及一条必须说清的安全事实

杠杆形态能力边界

ThemeTUI 主题纯展示层

需要注意 Extension API 的形态：它同时提供 registerProvider、registerTool、registerCommand、 on()、快捷键与 UI 组件——也就是说，扩展点和内核处在同一个抽象层级。 这就是为什么"让 Pi 帮你写一个扩展"是一条真实可行的路径，而不是宣传话术。

安全事实（官方口径，必须转述） Pi packages 以完整系统权限运行——Extension 会执行任意代码，Skill 也能指示模型执行任意指令。 它和 VS Code 插件不同，没有沙箱。 官方文档原话是"安装前认真看一眼来源"，而社区整理者的补充更直接："热门"不等于"审核过"。 这是在接入设计里必须写进文档的一句话：能力越开放，默认值越不能友好。

3.1.5　对内接：委派是"可选包"，不是内核能力

这是 Pi 与 DSH 最鲜明的对照点，也是理解两者哲学差异的最佳切口：

PiDeepSeek Harness
子代理的归属内核明确不做；由社区包 pi-subagents（周下载约 75K）用 Extension 实现内核 seam：ctx.subagents，六个官方 provider 一等公民
公开接口面刻意很小：一个工具 subagent + 一个命令 /subagents一组服务 + 一组工具（subagent / subagent-control）+ 控制工具（send_message / interrupt_agent / list_agents）
默认行为安装后不会自动启动后台 reviewer；只是给了 Pi 一个委派工具。想让每次都审查，就写进 prompt 或项目指令外部 provider 默认 disabled: true，装进 profile 并重启前不启动任何进程

pi-subagents 的工程细节里有几处直接可抄的设计：

  • 内建角色分工（用自然语言即可调用，不必先学配置）：scout 快速代码侦察（相关文件、入口、数据流、风险、下个 agent 该从哪儿开始）／researcher 带来源的文档调研／evidence-auditor 独立核验研究结论是否真的被来源支持／planner 只读规划／worker 实现（会验证，遇到未批准的决策升级而不是猜）／reviewer 审查／oracle 行动前第二意见（挑战假设、不改代码）／delegate 轻量通用。 官方经验法则：理解代码前用 scout，信外部事实前用 researcher，大改动前用 planner，实现用 worker，检查用 reviewer，决策本身有风险时用 oracle。
  • 统一的后台执行机制：没有另一套前台执行实现——默认的同步调用也是启动 detached runner、等这一次 run、返回完整结果。前台 run 在对话里流式显示，后台 run 在独立进程里继续跑、可稍后查看。
  • 等待是工具的一个 action，不是新工具：subagent({ action: "wait" })；语义上有讲究——无 id 快照当前会话的活动 run，默认在第一个完成或需要注意时返回；all: true 等全部；id 精确匹配或唯一前缀；无活动匹配立即返回；没有编排超时；取消父级 turn 只停等待、不停 detached runner。 官方明确反对反模式："不要写 sleep 循环或反复轮询状态来等待。"
  • 三层独立的有界性：maxSubagentSpawnsPerRun 限制一棵 run tree 的累计逻辑子代（默认 64），它与"活跃并发上限"和"session 级累计 spawn 预算"是三个彼此独立的维度。这种"把不同的限制拆成不同的旋钮、而不是合成一个数字"的做法值得照搬。
  • 可观测性内建：TUI 编辑器下方有常驻 FleetView；/subagents-fleet 打开实时检查器，可浏览子代、读 transcript、steer 运行中的子代、停止 run；/subagents-doctor 自检配置是否正确。
  • 并行隔离：worktree 字段可把并行任务放进 git worktree 隔离；context: "fresh" | "fork" 显式选择子代是否继承父级上下文——注意这与 DSH 的 inheritsParentContext 是同一个问题的两种命名。
Pi 在这件事上的真正洞察 Pi 把"要不要有子代理"从内核必须回答的问题，重新定义成一个可以安装、可以替换、可以自己写的问题。 代价必须一起说清：编排语义（多个扩展共同 follow-up 时怎么合并、进程恢复后回调里的临时状态怎么重建、预算与 Goal 由谁持有）会落在宿主和包作者身上。 如果不同扩展分别定义 Goal、Plan 和审批流程，结束语义会逐渐碎片化。 这不是缺陷陈述，而是选型判据：Pi 适合"单次 invocation 生命周期清晰、宿主已有自己的持久化层"的场景。

另外还有一条更轻的路线可以顺带记住：社区还有 pi-mcp-adapter（读 .mcp.json 把 MCP server 接进 Pi，支持惰性连接与工具元数据缓存）、 pi-web-access（网页访问，供 researcher 子代理使用），以及用 NATS 把 Pi 与 Claude Code 连起来互发消息的 bridge-harness。 Pi 的"没有 MCP"从来不是"不能有 MCP"，而是"不由内核替你决定"。

3.1.6　对外接：provider bridge —— 把外部 Agent 伪装成"一个模型"

社区（如 pi-omniagent-extensions）给出的方案非常统一：写一个 provider bridge 扩展， 让外部 Agent（Cursor / Codex / Claude Code / Rovo Dev）的模型出现在 Pi 的 /model 选择器里。 选中后，Pi 把对话路由给外部 Agent，流式取回回复，渲染成一条正常的 assistant 消息。

3.1.7　上下文桥接：bootstrap + 增量 + 压缩重置

外部 Agent 有自己的会话历史，扩展只能发"新的东西"。这套记账逻辑值得借鉴：

  • 首轮 → bootstrapPrompt：Pi 的 system prompt + 一条"bridge note"（告知 Agent 它正被 Pi 驱动）+ 把完整对话渲染成文本。
  • 后续轮 → incrementalPrompt：只发上次之后的消息增量。
  • sentMessageCount：记录有多少 Pi 消息已转发，避免重复。
  • 压缩事件 session_compact：外部会话重置，下一轮重新 bootstrap 全量上下文。

3.1.8　Agent Loop 的结束语义：双层循环 + 三个回调

Pi 的 runLoop() 使用内外两层循环，与 DSH 的五层边界（模型请求 / step / turn / driver activity / 长期工作流）形成清晰对照：

  • 内层条件：hasMoreToolCalls || pendingMessages.length > 0 —— 处理工具回访与 steering。
  • 外层：内层耗尽后调用 getFollowUpMessages()；有 follow-up 就设为 pending 重新进入内层，没有则发出 agent_end。
  • 一次内层迭代：prepareNextTurn → 处理 pending steering → 调用模型 → 执行工具 → 发出 turn_end → shouldStopAfterTurn → 拉取新的 steering。

Pi 只暴露三个高杠杆控制点，其余交给宿主：

回调职责与 DSH 的对应
getSteeringMessages()当前 activity 内的即时干预（Enter 发送的 steering 会在当前工具执行完后投递，并中断剩余工具）DSH 的 next-step inbox
getFollowUpMessages()Agent 自然收口之后的补充工作（Alt+Enter 发送的 follow-up 会等 Agent 停下才投递）DSH 的 next-turn inbox + Goal Driver
shouldStopAfterTurn()宿主级截停点DSH 的 agent/turn-stopping hook + Plan/审批层

几处值得对照的实现选择：

  • 超长输出的恢复哲学不同：stopReason === "length" 且消息含工具调用时，Pi 会给所有工具生成错误结果（说明参数可能被截断、没有实际执行）并交回模型，让它在下一 turn 重发完整调用； DSH 则整轮以 max-tokens 收口（且该 reason 具有粘性），把"是否继续"交给外部策略。 前者倾向在当前 invocation 内自我修复，后者保留清晰的 durable turn reason。有写操作的 Agent 更适合后者——达到输出上限本身意味着模型状态不完整，自动延续可能重复前一批操作。
  • 工具收口是 AND 聚合：finalizedCalls.length > 0 && finalizedCalls.every(r => r.result.terminate === true)。 只有非空批次中每个 finalized result 都带 terminate: true，整批才终止。 对比 DSH 的 concludesTurn 是 OR 聚合（任一权威工具即可宣布收口，再用 next-step 上下文缓和其侵略性）。 选 OR 还是 AND，取决于 terminate 的业务含义：若它表示"任一工具发现全局终止条件"，OR 合理；若表示"当前工具不需要模型处理自己的结果"，AND 更稳妥。
  • 并行执行、顺序提交：Pi 的并行工具用 Promise.all 保留输入数组顺序，最终 tool result message 按原调用顺序发出；DSH 的调度器维护 nextToStart / committed / slots 做 commitReady()。 两套系统都接受并行执行带来的延迟收益，同时拒绝让完成时序污染模型上下文。
  • 原因体系的粒度不同：Pi 主要保留 assistant message 的 stopReason（stop / length / toolUse / error / aborted），更接近"最后一次模型调用的结束事实"，利于分析模型行为； DSH 的 TurnEndReason 六态（completed / blocked / max-tokens / aborted / error / interrupted）聚合了多 step turn 的结果，利于分析任务执行。生产系统通常两类数据都需要。
Pi 在这件事上的自我定位很清楚：它提供一个"小而可组合的运行时"，没有承诺统一的长期任务协议。 复杂度被交给宿主——多个扩展共同提供 follow-up 时需要上层决定合并方式；进程恢复后回调内部的临时状态如何重建，也由应用实现。

3.1.9　供应链安全：一个被严重低估的工程样本

Pi 在"极简"之外还做了一件很少被提及、但极其可复制的事：把依赖供应链安全做成了一份清单。 对任何要"安装第三方 Agent 包"的系统，这套措施可以直接照搬：

措施具体做法

最小发布年龄.npmrc 设 min-release-age=2，避开当天发布的依赖——这是防投毒（typosquatting / 账号接管后快速发版）最便宜的一招

3.1.10　Pi 的边界与代价

必须一起看的四点代价 ① 开箱能力弱于 Claude Code / DSH：装好就用的完整体验是有代价的，Pi 需要你花时间配置才达到理想状态； ② 能力被"扁平化"（在对接外部 Agent 时）：外部 Agent 在 Pi 眼中只是一个"模型"，Pi 无法约束它的工具、深度、人设； ③ 安全边界被转移：无沙箱、无权限弹窗、packages 全权限、桥接扩展默认 auto-allow，"没有权限弹窗"不等于更安全； ④ 上下文重放成本：每次 bootstrap 都把全量对话塞进一个可能更贵的模型。

Pi 的哲学是"不替你隐藏边界"——极简不是没有边界，而是不替你隐藏边界。代价是这些边界必须由你自己画。 用官方的话收尾：Adapt Pi to your workflows, not the other way around.

3.2DeepSeek Harness：把外部 Agent 做成一等能力缝 重点

DSH（@deepseek-ai/dsh，npx @deepseek-ai/dsh web 一条命令启动）于 2026-08-13 以 MIT 协议开源，属 Developer Preview。 它的自我定位不是"DeepSeek 版 Claude Code"，而是一套关于 Harness 应该如何组织的答案。 规模上：226 个 npm 包、23.6 万行源码、21.7 万行测试、215 篇文档、1372 篇决策记录、52 件工具； 对外仓库只保留一个压缩后的 commit，内部 PR 编号已到 2519。这种"高成本组织方式"本身就是一个信号： DeepSeek 希望模型适配器、工具、存储、沙箱、Agent Loop 甚至 UI 都能独立替换。

3.2.1　底座：Cordis 与"一切皆插件"

DSH 的底座是 Cordis（由 Koishi 机器人框架作者 Shigma 开发，被 DSH 以 vendor 方式引入）。 它的核心主张是"没有特权内核可打补丁"——一个运行中的 dsh 实例，就是一棵从配置组合出来的插件树。

能力缝（Capability Seam）：替换的真正单位

DSH 里"可替换的单位"不是工具，而是 seam。一条能力被拆成三个角色， 官方态度很硬："单独一个角色不构成缝；增加一种能力意味着三个角色都要设计。"

角色职责落盘场景的例子
Service Definition定义接口与共同词汇，不含实现dsh-spill 定义存储契约
Service Provider提供某一种具体后端dsh-spill-local 把内容写到本地文件
Consumer把能力交给模型，通常表现为工具或策略dsh-spill-policy 判断哪些工具结果需要转存

这样拆包是为了控制发布边界：第三方想替换存储后端，只需依赖定义包，不必把整棵插件树带进项目。 压缩、沙箱、子 Agent、代码运行时、Skill 全部沿用同一套切法。

共享执行世界：seam 相比"独立工具"的实际收益 filesystem 与 subprocess 这类 provider 可以共享同一个执行世界。把 sandbox provider 切到远程环境时， Bash、PTY、LSP 会一起迁移，而不需要分别 fork 出 Remote Bash、Remote PTY、Remote LSP。 本地演示时这个差异可以忽略；一旦要接远程沙箱、容器或集群，它立刻变成决定性优势。

3.2.2　核心：ctx.subagents —— 接外部 Agent 的能力缝 重点中的重点

DSH 接外部 Agent 的机制全部收敛在一个服务上：ctx.subagents。 它是一个按名称注册的注册表（named-provider registry），与 ctx.llm、ctx.tools 同级。 官方文档里藏着最关键的一句设计判断：

"多数能力缝同一时刻只有一个活跃实现（例如 ShellExecutor 通常由一个 provider 支撑）。Subagents 不同：ctx.subagents 明确是一个注册表， 可以同时注册多个 provider，由调用方按任务选择委派给哪一个。"

这就是 DSH 与其他三家最本质的区别：它不认为"选哪个外部 Agent"是配置项，而是认为它是一次调用级别的决策。

subagent-codex 包内自带 Codex 进程（app-server --stdio） 否；临时 thread、单轮 否；仅原生 Profile permission mode 一次性（中断 turn 后 join 进程树，无回滚）
subagent-claude-code Agent SDK query + CLI 进程 否；inheritsParentContext: false 否；仅原生 permissionMode 一次性（Abort query + 终止进程树，无回滚）

① 静态能力描述符：五个 flag 定义"这个 provider 能做什么"

interface SubagentCapabilities {
  readonly agentOptions: boolean   // 能否强制外部 agent 的模型选项
  readonly outputSchema: boolean   // 能否返回结构化输出（而非自由文本）
  readonly depthLimit: boolean     // 能否限制子 agent 继续委派的层数
  readonly toolFilter: boolean     // 能否限定子 agent 可见的工具面
  readonly persona: boolean        // 能否覆盖子 agent 的 system persona
}

能力发现是静态的——在 provider 启动前就已确定，而不是运行时试探。 这带来一个高频"困惑点"，也是 DSH 设计上最值得抄的一处：同样一个 agentOptions 参数，行为完全不同—— 进程内 provider 会把它"合并到父 Agent 选项之上"，而 ACP / Codex / Claude Code 三家会在启动传输前直接拒绝。 官方解释是："你无法把模型选项强加到别人的产品上。"

这是设计，不是 bug UNSUPPORTED_CAPABILITY 的行为选择是"报错，而不是静默近似"。 官方措辞是：那些 provider"拒绝本地可选控制，而不是悄悄做个近似"。 对上层自动化来说，这个选择意味着：你不能假设 outputSchema 全局可用， 编写依赖结构化输出的编排逻辑时必须捕获异常分支。这比"看起来能用、结果格式悄悄变了"要安全得多。

② inheritsParentContext：一个字段解决一类系统性误解

这是整套设计里我认为最精妙的一处语义契约。官方对它的定义刻意窄化：

"inheritsParentContext 只意味着对话播种。它不意味着子 agent 继承了父级的工具、权限决策或授权。"

同理，工具过滤也只是改变了子 agent 注册的工具面，它不是"操作系统或外部账号边界已被包含"的证明。 这两句话说清楚了多 Agent 系统里最容易被想当然的两件事：上下文继承 ≠ 权限继承，工具过滤 ≠ 安全隔离。

各 provider 的实际语义：

  • fork：注入父级"平衡的已完成轮次前缀"作为对话种子。但不能假设正在进行的父级 turn 被复制了。
  • spawn：从零开始，只接收委派任务描述。
  • acp / codex / claude-code：外部 provider 报告 inheritsParentContext: false，收到的是一个独立文本任务 + 父会话工作目录，别无其他。
直接推论：每次外部委派都是冷启动 "任务文本必须自己携带子 agent 需要的一切"，而委派的成本 = 在更贵的模型上重建上下文的成本。 这是把外部 Agent 当作子能力时最现实的约束，也是为什么"该不该委派给 Claude Code"本质上是一道采购/经济学问题而非纯技术问题。

③ 双生命周期：一次性 vs 可继续

一次性（One-shot）可继续（Continuable）
生命周期单轮跑完即返回结果，由调用方通过 SubagentRun 句柄持有建立跨多轮的持久会话，由 SubagentContinuationManager 管理
适用父级下一步立即依赖这个结果子 agent 后续还需要 FIFO 补充指令
控制手段—send_message（入队下一轮，从不打断当前轮）、interrupt_agent（仅停当前轮，保留排队消息，已发布的子代继续运行）
重要语义四个可选能力（outputSchema / depthLimit / toolFilter / persona）必须由 provider 显式声明支持"一个 listed as ready 的 storage-only 子 agent 是可恢复的，不是等着被收集的完成结果"

④ 停止阶梯与"无回滚"：把不可逆性写进文档

每个 provider 的终止策略都是显式声明的一串降级动作：

  • ACP：ACP cancel → EOF 宽限 → SIGTERM → SIGKILL（协作式 teardown ladder）
  • Codex：中断 turn，然后 join 进程树；no rollback
  • Claude Code：Abort query 并终止进程树；no rollback
  • dsh-sdk：协议 shutdown → EOF → 进程终止

把"没有回滚"这四个字明确写进能力矩阵，是非常成熟的做法。 外部 Agent 可能已经产生了不可逆副作用（改了文件、发了请求、产生了费用）， 此时"重试"的不是一次函数调用，而是整个副作用序列——文档必须让调用方知道这一点。

⑤ 三条被验证过的"反直觉"设计

设计做法为什么反直觉 / 为什么对
不查 PATH 各 provider 包自带依赖（subagent-claude-code 打包官方 Claude Agent SDK，subagent-codex 打包 @openai/codex），启动自带的平台 payload。不检查 PATH、不做平台选择、不回退到宿主的 CLI。 直觉认为"用用户装好的更省事"，但那会引入不可控的版本漂移。装插件即装 CLI，用户只需要提供登录。pnpm-workspace.yaml 甚至为这两家 SDK 的平台二进制单独开了供应链策略例外。
认证原生透传 Claude Code 读取用户/项目/本地设置（相对于父会话工作目录），DSH 既不复制这些文件，也不创建登录状态。它只覆盖一个东西：permissionMode。 "统一管理凭证"看起来更干净，但会让被委派 Agent 以"另一个身份"运行，破坏用户的心理模型。让委派 Agent 以你本人、你的账号、你现有配置运行，是最小惊讶原则。
默认关闭 两个外部产品 provider 都不在任何 shipped bundle 里，preset 工具行带 disabled: true，注释写着"Production dsh does not install these optional providers"。它们是惰性 provider：装进 profile 并重启前不启动任何进程。 可扩展性越强，默认值越要保守。安全默认 > 开箱可用，尤其当能力是"以你的身份调用一个能改你文件的昂贵模型"时。

plan 这个模式是整套设计里最漂亮的一处： 它用一次配置完成了一次"能力降维"——把一个全权 Agent 降级成一个只读顾问。 注意它还堵住了"原生设置预先批准跳回执行"这条侧门，说明设计者认真想过 配置优先级被绕过 的攻击面。

⑦ 血缘与作用域正交

子 Agent 不继承父级的 agent-scope（隔离"哪个 agent 能看到哪些工具/提示/变量"的机制）。 作用域隔离与委派血缘是两个独立系统：血缘通过 parentSession 与 delegationDepth 字段单独追踪。 每个子 Agent 拿到的是"新的扁平作用域，而非继承父级注册"。

这个正交设计避免了"用作用域树兼职表示血缘"导致的两种错误： 要么血缘信息被作用域继承语义污染，要么为了保留血缘被迫继承不该继承的工具。

⑧ 三种委派形态的边界：Subagent / Job / Workflow

DSH 刻意不把三件事合并——这是"可靠多 Agent 系统不该塌缩"的三个关注点：

  • Subagent provider → 创建并拥有一个子执行边界
  • Job registry → 把一个后台运行暴露给它的所属父级（本地 Job 注册表默认每个精确 owner 最多 10 个运行中 + 停止中的 Job，超出直接拒绝；不排队、不抢占）
  • Workflow engine → 协调大量有界子调用并返回一个 JSON 值
两条重要的安全澄清 ① Workflow 的 worker 不是安全沙箱；② Workflow 的运行在进程重启后无法恢复。 另外 Ralph（面向不可变目标的迭代循环）的每一轮都是全新子会话，既不继承父级也不继承任何前序子 agent 的对话， 跨越轮次的只有共享工作区 + 一份有界 handoff（status / summary / evidence / next steps / blockers）。 上下文永不被污染，代价是记忆必须落在文件里。

3.2.4　一个真实的缺口案例：能力接入 ≠ 契约接入

AgentRQ 为 DSH 写的委派插件，暴露了一个所有"接外部 Agent"设计都该校验的问题。 AgentRQ 的 MCP server 把协作规则作为 server 级 Instructions 下发—— Claude Code 和 Gemini 会自动读取这些 Instructions，但 DSH 不会把 MCP server 的 Instructions 暴露给模型。 结果是：模型有了工具，却没有工具背后的契约（"人类是远程的、只能看到 reply 发出去的内容、开工前必须先 updateTaskStatus"）。

插件的解法是自己在 system-prompt 里补一段契约：

You are connected to an AgentRQ workspace through the mcp__agentrq__* tools.
The human you work with is REMOTE: they see only what you send with mcp__agentrq__reply.
Your terminal output, your files, and your reasoning are invisible to them.

Start: when you pick up a task, call mcp__agentrq__updateTaskStatus with
       ongoing before doing anything else ...
Finish: send a summary of every change, then set the status to completed.
Use blocked when you are stuck and need the human.

这带来两条可迁移的经验：

  • 工具名必须由命名空间生成，不能硬编码。该插件 section 里每个工具名都从 bridge 配置的 namespace 生成—— "改 bridge 名字时，指引与实际注册的工具不会漂移"。这是一条很硬的工程约束。
  • 软契约（Instructions / 行为约定）需要一个显式的传递通道。如果宿主不转发，就必须由接入方自己补。 在接入设计里，"哪些元信息会被传给模型"必须被列为验收项，而不是默认协议会处理。
还有一个架构级取舍值得注意：一个 profile 服务一个工作区 AgentRQ 的答案是"架构上解决，而不是加配置开关"—— 每个 DSH profile 只服务一个工作区，endpoint 固定在那个 profile 自己的 cordis.patch.yml 里。 切换工作区就是切换 profile，不存在一个共享环境变量被误设、导致 A 工作区的会话打到 B 任务队列的可能。 另外 scope: single-agent 默认值解决了"Web UI 每开一个 tab 就建一个 root agent、导致任务被投递三次"的问题。

3.2.5　DSH 的边界：本地优先带来的约束

DSH 的产品边界非常明确，且直接决定了它的架构选择：面向单用户、以一个工作目录为根、用户自带 API key、通过 CLI / Web UI / ACP / JSON-RPC SDK 使用；暂时不负责计费，也没有先处理多租户与云端托管。

这套边界让一条核心不变式得以成立：

"模型可见的内容，必须已经被记录。"任何进入模型请求的内容，都必须能够从 SessionEvent 日志重建。 系统要增加一种新的模型输入，就要先增加对应的事件类型。

这条不变式很美，但报告里明确点出了它在多租户下的失效边界：

  • 本地工具场景：用户持有所有数据，"模型可见 = 已记录"很容易成立。
  • 多租户 SaaS 场景：用户消息和工具结果属于租户，而 Skill 正文属于平台——Skill 需要进入模型请求，但不能写进租户数据库、也不能随会话导出被用户带走。 于是数据库只保存 Skill id，模型回放时再从平台注册表加载正文。
结论 这不是对事件日志的否定，而是数据所有权带来的边界。 对本地逻辑与多租户逻辑必须分开设计：模型请求视图与持久化记录，有时必须分离。 如果我们的 Harness 未来要做多租户，这一条要提前规划，不能事后补。

3.3OpenAI Codex：唯一的"双向 MCP"

Codex 的特殊价值在于它同时站在 L1 的两端：既作为 MCP client 消费外部工具，又作为 MCP server 被外部系统编排。 这使它成为 DSH 的 subagent-codex 能存在的前提。

3.3.1　作为 MCP client（往外接）

维度细节
配置位置~/.codex/config.toml 的 [mcp_servers.<name>] 表；也可用项目级 .codex/config.toml（仅对被标记为 trusted 的项目加载）

3.3.2　作为 MCP server（被接入）

一行命令把自己变成可被编排的节点：

codex mcp-server          # 以 stdio 方式启动为 MCP server
# 继承全局 ~/.codex/config.toml 设置；下游 client 关闭连接时终止
# 调试：npx @modelcontextprotocol/inspector codex mcp-server

对外只暴露两个工具，这个克制的设计值得注意：

工具参数说明
codex()
开始会话		 prompt（必填）、approval-policy、sandbox、model、base-instructions、cwd、config 发起一个新的 Codex 会话。响应中 structuredContent.threadId 是续会话句柄
codex-reply()

关键设计点：把 approval-policy 与 sandbox 做成"每次调用的参数"而不是"进程级配置"。 调用方（上层编排器）因此可以按任务逐次收放权限：read-only / workspace-write / danger-full-access， untrusted / on-request / never。这与 DSH"策略随调用携带，而不是固定在 provider 上"的思路完全同源—— 同一个瞬间，bash 可以 readonly，而子 agent 的状态目录保持可写。

为什么需要走进程外边界 Codex CLI 原生 subagents（config.toml 里的 [agents]）已经支持并行，但它们运行在同一个 Codex 进程内、共享同一套沙箱策略，且受 agents.max_depth（默认 1）限制。 当需求是①跨语言编排（Python 编排器委派 Codex 写 TS）、②带门禁的交接（PM agent 验证产物存在后才放行下一个 agent）、 ③异构模型（规划用 GPT-5、实现用 GPT-5.5、快速 lint 用 o4-mini）、④统一 tracing 时， MCP server 才是正确的抽象。

生态侧还有 codex-as-mcp 这类社区 server，向 MCP client（Claude Code、Cursor 等）暴露 spawn_agent(prompt) 与 spawn_agents_parallel(agents) 两个工具，底层执行 codex exec --cd ... --skip-git-repo-check --full-auto "..."。 其 README 有一句诚实的安全提示值得引用："--full-auto 意味着 agent 可以在该目录运行命令并编辑文件。只在你信任的仓库中使用。"

协议侧，Codex 原生支持 MCP；ACP 由社区项目 codex-acp（Rust 实现的适配器）桥接， 自 2026-01 ACP Agent Registry 上线后，Codex 已在 JetBrains 与 Zed 中通过注册表可安装； A2A 在 Codex 侧仍是 open feature request。

3.4Claude Code：把自己做成标准零件

Claude Code 的接入哲学与 DSH 相反——它不做"接别人"的框架，而是把自己彻底组件化，让任何系统都能把它接进去。 四个扩展点构成了完整的"被接入面"。

扩展点接口要点

Subagents agents={"name": AgentDefinition(description, prompt, tools, model)} 每个子 agent 有独立上下文窗口、工具集与 system prompt；主 agent 通过 Agent 工具（Python SDK 里是 Task）触发委派，必须在 allowed_tools 里包含它。子 agent 的消息带 parent_tool_use_id，可追踪来源
MCP mcp_servers 支持本地 stdio（作子进程）与远程 Streamable HTTP / SSE；也支持进程内 SDK MCP server（create_sdk_mcp_server） 工具命名规范 mcp__<server>__<tool>。SDK MCP server 与外部 server 可混用。SDK 下 MCP 工具必须在 allowed_tools 显式列出（如 mcp__github）
Skills .claude/skills/*/SKILL.md（项目）与 ~/.claude/skills/*/SKILL.md（用户） 基于文件系统，必须显式启用：SDK 下需设 setting_sources=["user","project"]，否则即使 Skill 在 allowed_tools 里也不会被发现——这是官方点名的常见错误

权限模型的表达方式

SDK 用三层组合表达权限，比单一开关更细致：

  • allowed_tools：只列出的工具可用，省略某个工具即等于封禁；完全不传则 agent 只能推理、无任何工具
  • blocked_tools：即使已在 allowlist 中也可显式封禁
  • PreToolUse hook：细粒度审批逻辑，可返回 permissionDecision: "deny" 与理由

生产建议是"把 allowed_tools 设成最小必要集，再用 hooks 叠加细粒度逻辑"。

它在被接入侧的定位

Claude Code 通过官方 ACP 桥（@agentclientprotocol/claude-agent-acp）进入 ACP 生态， 在 Zed 里以 @zed-industries/claude-acp 安装、首次使用时自动安装并通过 /login 认证； 在 JetBrains 里通过 ACP Agent Registry 安装。 同时它也是 DSH 的 subagent-claude-code 所接入的对象——DSH 通过 Claude 官方的 Agent SDK 拉起一个真实的 Claude Code CLI 子进程。

一个值得记住的生态事实 Claude Code 与 DSH 不是互斥关系。 在 DSH 架构下，外层循环跑开源模型，只在真正值回票价的少数任务上委派给 Claude Code， 并且所有这些轨迹都被收进同一份 session log。"三个产品抢一个机器上的位置"的叙事是不准确的——其中两个可以被当作另一个的子程序。

4Pi × DSH：两种 Harness 哲学的正面对撞 双重点对比

把 Pi 和 DSH 放在一起看，价值远大于分别看。两家都常被贴上"极简"标签，但它们对"复杂度应该放在哪里"给出了相反的答案：

  • Pi 的极简发生在内核：内核小到只剩四个工具、一条循环、一棵会话树，其余能力以可安装的外挂形式生长。
  • DSH 的极简发生在"内核的不可替换性"：它可以有 226 个包，但没有一个特权核心；代价是每条能力接缝都要求 Service Definition / Provider / Consumer 三件套齐全。

所以更准确的描述是：Pi 是"少而开放"，DSH 是"多而对称"。下面的对照不评判优劣，只定位边界。

4.1　一句话定位

Pi Agent

可嵌入的 Agent 执行内核。目标是把"一次 prompt 驱动的工具循环"做到最小、可读、可组合。 Sessions、Goals、Plan、子代理、审批——全部是宿主或第三方包的事，内核不承诺统一的长期任务协议。

DeepSeek Harness

事件溯源的 Agent Runtime。目标是让所有长期语义都在内核里闭合、可恢复、可审计。 Goal、Plan、子代理、权限、沙箱、压缩——都要有明确的生命周期与事件表达。

4.5　选型判据（不是"谁更好"）

Pi 的结构更适合

  • 单次 invocation 的生命周期清晰，不需要跨进程恢复
  • 宿主已经拥有自己的持久化层与状态管理
  • 扩展数量有限（尚未出现多插件同时 steering）
  • 工作流由应用统一控制，不需要内核协议保证
  • 目标是快速接入多模型与工具
  • 对 session event vocabulary 没有强约束

DSH 的分层更适合

  • 会话需要跨进程恢复
  • Agent 拥有高风险工具（写入、发布、付费）
  • 多个插件会同时 steering，需要确定性的合并规则
  • 需要长期 Goal 与预算控制
  • 日志需要审计与 replay
  • Plan、审批与执行必须跨边界保持一致
  • 子 Agent 与父 Agent 存在取消传播
本章最重要的一句话 复杂度没有消失，只是落在不同层。 如果业务开始增加 Goal、审批、自动 follow-up、并发工具策略、恢复与预算，Pi 的宿主会逐步补齐类似机制—— 这时再回头换框架，成本远高于一开始就选对分层。 所以选型时不应比较"Agent Loop 有多少行"，而要问：我的系统准备把"继续运行的权力"放在哪里？

6可借鉴清单：16 条具体设计

以下从四家方案中提炼出可直接迁移的设计条目，按"抽象 → 契约 → 生命周期 → 边界"排序。

1. 把"外部 Agent"抽象成 seam，而不是特例分支 抽象

不要写 if (isClaudeCode) {...} else if (isCodex) {...}。定义"委派"的 Service Definition，让每家实现一个 Provider， 调用方只面向 seam。判据：新增一个外部 Agent 时，是否只加一个包而不改核心代码。

2. 用注册表而非单例 抽象

多数能力缝只允许一个活跃实现，但"委派给谁"是调用级别的决策。把 subagent 做成命名注册表，允许多 provider 共存， 由任务特性选择。这也让"局部替换"成为可能——某类任务走 A，另一类走 B。

3. 静态能力描述符 + fail loud 契约

让 provider 在启动前声明它能做什么。调用方请求了不具备的能力时直接报错， 而不是静默降级。"看起来能用但结果悄悄变了"是分布式系统里最难排查的一类故障。

4. 为"继承"这类词写严格的语义契约 契约

inheritsParentContext 只在文档里被定义为"对话播种"，并额外声明"不代表工具、权限决策或授权的继承"。 给易被误解的字段配一条否定式定义，比只写肯定式定义有效得多。

5. 区分"上下文"与"权限"两条继承链 契约

上下文可以继承，权限默认不继承。工具过滤改变的是工具面，不是 OS 或账号边界—— 这条要写进文档，否则使用者会把它当沙箱用。

6. 血缘与作用域正交 契约

用 parentSession / delegationDepth 独立追踪委派链，不要用作用域树兼职表示血缘。 子 Agent 拿新的扁平作用域，避免"为了保留血缘而被迫继承不该继承的工具"。

7. 双生命周期 + 显式的续接语义 生命周期

one-shot（立即返回结果，父级阻塞等待）与 continuable（持久会话，FIFO 补指令）要分开建模。 并明确：send_message 是入队下一轮、从不打断当前轮；interrupt 只停当前轮、保留队列。

8. 分级停止阶梯 + 诚实地声明"无回滚" 生命周期

协作式 teardown：协议 cancel → EOF 宽限 → SIGTERM → SIGKILL。 并且明确告诉调用方：外部 Agent 可能已产生不可逆副作用，中断不等于撤销。

9. 依赖自带，不查 PATH 边界

让每个 provider 打包它需要的 SDK 与平台二进制，不检查、不回退宿主的 CLI。 换来的是版本确定性与可复现性——在"把任务交给另一个 Agent"这种长链路里，这一点比省事重要得多。

10. 认证原生透传，只覆盖一个旋钮 边界

不复制用户配置、不创建登录态，让被委派 Agent 以用户本人身份与账号运行。 只覆盖一个与安全直接相关的配置（如 permissionMode），其余一律不碰。最小惊讶原则。

11. 提供"降维"模式：只读顾问 边界

plan 模式是范本：让昂贵的全权 Agent 跑原生规划模式，拒绝执行审批， 并把"跳回执行"的入口从原生设置里禁用掉，只返回 plan。 "拿到判断力，但不给它文件系统。"

12. 软契约要有显式传递通道 边界

MCP Instructions 这类"行为约定"不会自动到达所有宿主模型。 接入设计里必须列出"哪些元信息会传给模型"作为验收项；同时把所有暴露的工具名从配置命名空间生成，避免指引与实现漂移。

13. 状态落在文件里，而不是工具内部 抽象 · Pi

Pi 刻意不内建 Plan mode / Todo / 后台 bash，理由是这些功能把状态藏进了工具内部。 替代方案统一指向文件：plan.md、TODO.md、用 tmux 管后台进程。 判据很简单：出问题时，这些状态你能不能自己打开看？换掉工具之后它还在不在？ 对我们要接入外部 Agent 的场景尤其重要——外部 Agent 的内部脉络本来就看不见， 至少我们自己的编排状态不能再藏起来。

14. 会话应该是树，可回退、可分支、可分享 生命周期 · Pi

Pi 的会话是 JSONL 树（每条带 id / parentId），所有分支在同一文件里； /tree 就地跳转到任意历史节点继续，/fork 从历史消息开出新会话文件， 切换分支时还能把被放弃的分支总结后附加到新位置，避免重放整条分支。 对比 DSH 的"只追加日志 + fork 截取前缀"：两者都在回答同一个问题—— 失败尝试不应该污染后续上下文，但也不应该被抹掉。多 Agent 编排里，"从某个分岔点重试一个委派"是高频需求，值得一开始就建模。

15. 把"委派"做成可安装的包，而不是内核承诺 抽象 · Pi

Pi 内核明确不做子代理，交给第三方包；该包的公开接口刻意只有一个工具 + 一个命令， 其余（专用角色、额外命令、提示模板）全部来自用户配置、项目或别的包。 这给我们一个中间选项：不确定某类委派该不该进内核时，先按"可选包 + 极小公开面"做， 等用法稳定了再考虑上收到内核。接口小，是给未来的自己留退路。

16. 供应链要精确锁定 + 设"最小发布年龄" 边界 · Pi

接入外部 Agent 本质上是引入一条不可信代码执行链。Pi 的清单可以直接照搬： 依赖精确 pin（save-exact）、.npmrc 设 min-release-age=2（避开当天发布的依赖，防投毒）、 lockfile 由 pre-commit hook 守护、发布包带 npm-shrinkwrap.json 锁死传递依赖、CI 跑 npm audit 与签名校验、install script 走白名单。 对应 DSH 的另一条路是"依赖自带、不查 PATH"，把风险集中到可审计的白名单。两条都要显式选一条，不能默认不管。

7落地建议：给 dongbi-agent-harness / AgentLoop v2 的四步路线

结合本项目现状（AgentLoop v2 六阶段 V00–V54、已有 Harness 架构设计），建议按以下顺序引入外部 Agent 接入能力。 顺序本身很重要——先建契约再建实现，否则后期会被各家差异反复打补丁。

7.1　具体落点建议

步骤交付物验收标准
1　建契约 SubagentCapabilities 类型（5 flag）；
SubagentProvider 接口（run() / capabilities / inheritsParentContext）；
SubagentRuntime 注册表服务（register / resolve(name) / list()）；
SubagentError 错误族（含 UNSUPPORTED_CAPABILITY） 		注册一个 Fake provider，请求一个它未声明的能力，能稳定拿到 UNSUPPORTED_CAPABILITY，且不产生任何副作用
2　接自家的 in-process spawn / fork 两个 provider；能力协商走通 fork 能正确注入父级已完成轮次前缀，且能验证"父级进行中的 turn 未被复制"；spawn 不继承对话
3　接外部的 先一个 ACP provider（覆盖面最广），再视需要接 SDK 类 外部 provider 声明 inheritsParentContext: false；带 agentOptions 的请求被拒绝而非忽略；依赖自带、不读 PATH；认证沿用用户原生登录态
4　收边界 安全默认开关；停止阶梯；只读降维模式；委派血缘字段 默认配置下外部 provider 不启动任何进程；取消能在 3 次信号内确定终止；文档明确写出"中断不等于回滚"；parentSession / delegationDepth 可从日志重建
如果只做一件事 先做第 1 步的 SubagentCapabilities + UNSUPPORTED_CAPABILITY。 理由：它成本最低、对现有代码侵入最小，却直接决定后续所有外部 provider 能否被安全地编排。 四家方案里，只有 DSH 做了这件事——而这恰好是它最难被模仿、也最值得借鉴的部分。

7.2　落地时先抄谁：一份分工建议

Pi 与 DSH 是两套不同重量的答案，不必二选一。结合本项目的实际阶段，建议按"哪一部分抄谁"来分工：

要解决的问题抄 Pi（成本低、见效快、可读）抄 DSH（成本高、换来长期确定性）
运行状态放哪 先抄 Pi：计划写 plan.md、待办写 TODO.md，让状态可打开、可版控。这一步几乎零成本，且立刻提升可调试性 等到需要跨进程恢复时，再引入只追加事件日志与"模型可见 ⟺ 已记录"的不变式
会话模型 先抄 Pi：JSONL + id/parentId 的树形会话，支持就地跳转与分支摘要。"从某个分岔点重试一次委派"是多 Agent 场景的高频需求，早做早省事 需要 fork / replay / 审计导出时，再补"只追加日志 + 前缀截取"的语义
循环继续的控制权 若宿主已有自己的调度层：抄 Pi 的三个回调（steering / follow-up / stopAfterTurn），扩展作者上手成本最低 若会出现多插件同时 steering：必须抄 DSH 的 inbox 数据驱动，否则布尔合并规则会失控
接入契约 — 直接抄 DSH：能力描述符 + UNSUPPORTED_CAPABILITY + inheritsParentContext + 双生命周期 + 停止阶梯。这一层 Pi 没有对应设计
供应链与默认开关 抄 Pi 的清单：精确 pin、min-release-age、shrinkwrap、lockfile 守护 抄 DSH 的姿态：依赖自带、不查 PATH；高危能力默认 disabled 且不进默认包
扩展体系 抄 Pi 的分级杠杆：Skill（说明书）/ Extension（新工具）/ Package（可分发的组合），并保持公开接口尽量小 若要长期开放给第三方，再补 DSH 的能力缝三件套（Definition / Provider / Consumer）与可逆副作用（effect 回滚）
一个务实的结论 先把 Pi 的三样东西拿到手（状态外置、树形会话、三个回调），成本极低且立刻改善可调试性； 再把 DSH 的一件事做扎实（能力描述符 + fail loud），这一件决定了外部 Agent 能不能被安全编排。 剩下的（事件日志、能力缝三件套、inbox）等到真的出现"跨进程恢复 / 多插件 steering / 高风险工具"这三类需求时再引入， 否则投入会超过收益——这本身就是 Pi 与 DSH 共同给出的判断：复杂度没有消失，只是要放在对的那一层。

8风险与未定项

风险说明应对
DSH 仍是开发者预览 GitHub / npm 当前为 dsh-v0.1.1-rc.1 级别，官方明确警告会出现破坏性变更；SDK 示例默认 danger-full-access，文档警告只能在一次性代码副本或容器中运行 借鉴设计模式而非直接依赖；若要试用，锁定 Profile、包版本、provider 配置与 commit
能力不对称 ACP / Codex / Claude Code provider 拒绝 agentOptions 等本地控制；outputSchema 并非全局可用 编排逻辑必须捕获 UNSUPPORTED_CAPABILITY 分支；不要假设能力普遍存在
权限边界错觉 工具过滤 ≠ OS / 账号边界；inheritsParentContext ≠ 权限继承 把"隔离"与"限制"分成两个概念建模；沙箱靠真机制（Landlock / container）
委派的经济性 外部委派是冷启动，成本 = 在更贵模型上重建上下文的成本；且中断无回滚 只把少数高价值任务委派出去；任务文本自带完整上下文；文档化"无回滚"
协议分裂与演进 MCP / ACP / A2A 三层并存，且 ACP v2 为 draft（schema-v2.0.0-alpha.3），要求实现方 v1 + v2 并行支持并做版本协商 接入层做协议适配隔离；版本协商在 initialize 阶段用 protocolVersion 完成，不要从库版本推断
供应链与平台二进制 自带依赖的方案需要在 workspace 层为平台二进制开放构建/供应链例外 提前规划依赖白名单与构建策略（pnpm ≥10 需在 profile 的 pnpm-workspace.yaml 里 allowBuilds）
第三方包的信任边界 Pi 生态的 packages/Extensions 以完整系统权限运行、无沙箱；反过来，"热门"不等于"审核过"。接入方若允许装包即多一种外部 Agent 能力，等于开放了一条任意代码执行链 把供应链清单变成默认护栏（精确 pin / min-release-age / shrinkwrap / lockfile 守护 / 签名审计 / 脚本白名单）；或走 DSH 的"依赖自带 + 白名单例外"路线
本报告的未验证与时效性 DSH 处于 Developer Preview（dsh-v0.1.1-rc.1 级别，官方警告破坏性变更）；Pi 迭代同样快（pi-subagents 版本在数周内从 0.28 走到 0.67）。subagent provider 的确切调用签名在公开材料中未固定；本报告未运行代码验证 动手前查 DSH 的 docs/subsystems/subagent.md 与 packages/subagent/、Pi 的 pi.dev/docs/latest 与 Extension 类型定义；锁版本后再评估
